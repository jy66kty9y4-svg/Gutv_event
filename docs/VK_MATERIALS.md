# Материалы VK

Раздел `/studio#latest-projects` показывает до пяти публикаций VK. Пять ссылок,
подтверждённых пользователем 5 сентября 2026 года, хранятся в
`app/vk-reference-posts.ts` в явном порядке: 6873, 6869, 6866, 6862, 6855.
Это порядок снимка страницы, а не вымышленные timestamps публикации: у трёх
первых из них дата намеренно пуста, у двух старых сохранено только «30 июля».

Callback `wall_post_new` сохраняет новые публикации сразу; повторная доставка
обновляет уже существующую запись по паре `group_id, post_id`. Запись Callback
с ID из reference-снимка обогащает ту же карточку, но не меняет её подтверждённую
позицию и использует локальный screenshot, если изображение не пришло. Только
неизвестные записи с датой позже момента снимка `2026-09-05T13:05:54Z` могут
встать перед snapshot. Старые неизвестные строки и другие группы не показываются.

Отдельная страница `/materials` перенаправляет в этот раздел. Её пункт меню удалён;
последние публикации показываются компактно на странице «О студии».

## Начальное заполнение

Скрипт `scripts/backfill-vk-materials.mjs` запрашивает до 20 собственных постов
группы и по умолчанию только
печатает безопасную сводку: ID, дата и наличие текста/изображения. Он не печатает
токен, текст постов или URL изображений.

```sh
GUTV_VK_BACKFILL_TOKEN='existing-user-token' \
GUTV_VK_GROUP_ID='30973272' \
node scripts/backfill-vk-materials.mjs --dry-run
```

После проверки выбранных ID запись выполняется только с `--apply` и явным путём
к SQLite-файлу:

```sh
GUTV_VK_BACKFILL_TOKEN='existing-user-token' \
GUTV_VK_GROUP_ID='30973272' \
GUTV_DATABASE_PATH='/data/requests.sqlite' \
node scripts/backfill-vk-materials.mjs --apply
```

Нужен уже существующий пользовательский токен, который VK разрешает использовать
для `wall.get`. Ключ сообщества подходит для управления Callback API, но
проверенный 5 сентября 2026 года вызов `wall.get` с ним вернул VK API ошибку 27
(`method is unavailable with group auth`). Поэтому ключ сообщества нельзя
использовать для истории стены. Новый ключ, новые права и запись в production не
входят в этот скрипт.

Флаг `wall_post_new` в настройках говорит только о том, что VK разрешено посылать
это событие. Он не подтверждает фактическую доставку: перед опорой на Callback
проверьте подтверждение сервера в кабинете VK, журнал доставок и появление новой
строки в `portal_vk_posts`.

## Восстановление Callback API при публикации

`scripts/restore-vk-callback.mjs` закреплён за группой `30973272`, сервером `4`
и URL `https://gutv.tech/api/vk/callback`. По умолчанию он только читает VK API
и сообщает состояние без кода или токена:

Из корня release:

```sh
node scripts/restore-vk-callback.mjs --check
```

Перед подтверждённым переключением `--prepare-code` получает код подтверждения
из VK и записывает ровно строку `GUTV_VK_CONFIRMATION_CODE=...` в защищённый
staging-файл с режимом `0600`. Его затем переносит release-процедура в приватное
окружение. Скрипт не меняет Callback-настройки в этом режиме.

После публикации с новым приватным окружением запуск `--enable-after-publish`
проверяет, что staging-файл и приватное окружение содержат тот же актуальный код
VK, сохраняет исходные `api_version` и все флаги событий в защищённый backup
`0600`, включает только `wall_post_new` на сервере 4 и снова читает настройки.
При ошибке он возвращает полный предыдущий набор флагов.
Этот режим меняет VK только после явного production-подтверждения.
Если `wall_post_new` уже включён, `--enable-after-publish` завершится с `no-op`
и не будет читать staging-файл или менять настройки VK.

## Проверка

```sh
node scripts/test-vk-materials.mjs
```

Тест запускает временную копию приложения с временной SQLite-базой. Он проверяет
редирект, все пять reference-ссылок без БД, добавление нового Callback-поста без
потери четырёх references, дедупликацию известного ID, fallback screenshot, а
также исключение чужой группы и неизвестной старой строки.
